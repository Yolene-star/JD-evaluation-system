# 全局交互基线设计

> 文档状态：已确认基线  
> 适用范围：阶段一 JD分析、阶段二模拟面试、阶段三人才画像  
> 设计前提：业务内容由Agent根据现场上下文动态生成；本文件定义的是页面结构和交互规则，不预设业务回答。

## 1. 设计目标

系统的主要交互方式是用户与主 Agent 的连续对话，结构化信息通过右侧阶段工作台同步呈现。用户既可以用自然语言提出请求，也可以直接操作工作台；两种方式必须修改同一份业务数据，并在对话区留下可回溯的系统操作记录。

前三个阶段使用同一套页面骨架、视觉语言和交互组件，用户只需要学习一次操作方式。阶段变化体现在右侧工作台的业务内容、当前状态和允许动作变化，而不是切换到完全不同的页面。

## 2. 已确认的全局方案

| 设计维度 | 已确认方案 | 目的 |
|---|---|---|
| 桌面页面骨架 | 折叠导航 + 平衡双栏 | 对话和结构化工作台同时可见，项目导航不抢占主注意力 |
| 对话信息分层 | 语义气泡 + 内嵌事件卡 | 保持自然对话，同时区分Agent回答、用户操作和证据 |
| 阶段导航 | 顶部线性阶段轨道 | 始终知道当前位置，并明确阶段前置条件 |
| 视觉方向 | 温和专业、成长陪伴 | 面向学生长期自测，降低压力并保持可信感 |
| 窄屏布局 | 桌面右栏常驻，窄屏右侧滑出 | 保留侧边工作台关系，避免手机双栏挤压 |
| Agent回答 | 依据现场动态生成 | 避免预置话术冒充真实推理和项目结果 |

## 3. 页面结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 项目名称 / 阶段轨道 / 当前版本 / 可信度或完整度 / 用户菜单      │
├─────────────┬──────────────────────────┬─────────────────────┤
│ 折叠导航    │ 主对话区                 │ 阶段工作台           │
│             │ Agent动态回答            │ 当前阶段结构化内容   │
│ 项目入口    │ 用户消息                 │ 表格、图表、状态     │
│ 轻量阶段入口│ 系统操作卡片             │ 证据抽屉             │
│             │ 证据引用卡               │ 操作按钮             │
│             │ 输入区                   │                     │
└─────────────┴──────────────────────────┴─────────────────────┘
```

### 3.1 顶部栏

顶部栏在三个阶段保持相同位置和层级，展示：

- 当前项目名称。
- 阶段轨道：JD分析、模型确认、模拟面试、人才画像。
- 当前绑定的数据版本和Prompt/规则版本摘要。
- 可信度、证据完整度或面试完成度等当前状态。
- 用户菜单、导出和数据管理入口。

阶段轨道允许查看已完成阶段，但未满足前置条件的阶段不可跳转。点击不可进入阶段时，使用动态生成的原因说明；按钮、状态标签等确定性界面反馈可以采用固定文案。

### 3.2 折叠导航

桌面端默认使用窄导航轨道，包含新建任务和历史任务入口。展开后直接罗列最近历史任务；每条任务显示任务名称、所属阶段、处理状态和最近活动时间。当前任务不单独设置入口，而是在历史任务列表中高亮。点击历史任务后恢复该任务对应的对话与工作台状态，但不改变其他任务的数据。

折叠导航的交互原型已验证：折叠状态仅保留新建任务、历史任务和展开入口图标，并通过悬停或键盘焦点显示文字提示；展开状态显示历史任务列表。当前任务使用高亮状态，历史任务按最近使用时间排序；默认只显示最近几项，任务过多时通过“查看全部历史任务”进入完整列表。帮助与账户设置不放入当前项目导航。展开与折叠不改变当前阶段或工作台内容。移动端不保留常驻导航栏，改为从侧边滑出的导航面板。

导航不是业务状态机的替代品。阶段能否进入由后端状态决定，前端只展示状态并发起合法请求。

### 3.3 主对话区

主对话区是全局主线，三个阶段都保留连续上下文。输入区支持文本、上传、链接等当前阶段允许的入口；不允许的入口仍显示，但必须说明原因或提供可行替代动作。

Agent每次业务回答的上下文至少包括：

- 当前项目和阶段状态。
- 当前绑定版本和允许动作集合。
- 用户最新意图。
- 与本轮相关的结构化数据。
- 需要引用的证据。
- 必要的对话摘要。

不得通过关键词命中预先编写的完整业务回答。不同项目、状态、证据或用户意图必须能够产生与现场一致的不同回答。

### 3.4 右侧阶段工作台

桌面端右侧工作台常驻，可收窄或拖动宽度，但不能小于保证表格、按钮和证据内容可读的最小宽度。工作台使用统一标题层级、卡片边界、表格密度、状态标签和操作栏。

三个阶段只替换业务内容：

- 阶段一：JD列表、单JD解析、总胜任力模型、冲突和待确认项。
- 阶段二：面试设置、进度、当前问题、提示记录和面试状态；不显示实时评分细节。
- 阶段三：人才画像、雷达图、能力评价、证据矩阵、报告结论和回溯入口。

## 4. 对话内容类型

### 4.1 Agent动态回答

使用自然语言气泡展示。回答可以解释、询问、建议、总结或反馈动作结果，但必须依赖现场数据。回答引用业务对象或证据时，显示可点击的对象编号或证据编号。

### 4.2 用户消息

保留用户原文，并记录时间和所属阶段。用户的普通请求、确认、修改和澄清必须可区分，便于审计与后续评价。

### 4.3 系统操作卡片

用户通过工作台执行上传、删除、合并、修改权重、确认模型等操作后，对话区立即插入系统操作卡片。卡片至少显示：动作、对象、结果、时间、操作者和恢复入口。

示例：

```text
已更新：合并“用户需求分析”和“需求调研”
影响：总模型能力项 18 → 17
依据：两项来自 3 份 JD 的同义表达
[查看影响] [撤销]
```

操作卡片是系统事件的视觉表达，不是用户观点，也不能被送入面试评分上下文当作用户回答。

### 4.4 证据引用卡

证据卡默认折叠，展开后展示来源、原文片段、定位、关联对象和解释。阶段一展示JD证据，阶段二展示问题与回答证据，阶段三展示结论到证据的完整链路。

## 5. 统一交互规则

1. 对话和工作台实时同步，刷新后状态不丢失。
2. 工作台操作和对话命令写入同一领域事件，并保存前后状态。
3. 高影响操作先显示结构化预览，需要用户确认后执行。
4. 可逆操作提供撤销；撤销本身也是一条新的事件，不能删除历史记录。
5. 长任务显示处理步骤、当前状态和可恢复动作，不只显示“AI处理中”。
6. 错误提示靠近发生位置，同时提供重试、重新上传、改用其他入口或继续保留已有结果等方案。
7. 任何阶段转换都由后端状态机校验，前端不能仅靠隐藏按钮保证安全。
8. 进入下一阶段后绑定不可变版本；历史结果继续保持原版本语义。
9. 对话滚动位置、未发送草稿和打开的证据状态在合理范围内保留。
10. 用户可查看、导出和删除自己的项目数据。

## 6. 窄屏响应式规则

### 6.1 桌面端

- 折叠导航 + 对话区 + 右侧常驻工作台。
- 工作台支持收窄和拖动，但保证对话输入与结构化内容不重叠。
- 证据抽屉在工作台内部打开，必要时覆盖工作台内容。

### 6.2 平板端

- 根据可用宽度，在右栏常驻和右侧滑出之间切换。
- 进入面试时优先保证对话区和输入区宽度。
- 不使用横向滚动承载核心操作。

### 6.3 手机端

- 默认显示主对话区。
- 底部提供“对话”和“工作台”入口；点击工作台后从右侧滑出。
- 面板在窄屏上可以接近全屏，但必须保留右侧进入关系、关闭按钮和返回对话入口。
- 打开面板时锁定背景操作；关闭后恢复原对话滚动位置和输入草稿。
- 键盘焦点进入面板，关闭后回到触发按钮。
- 支持减少动效模式，减少动效时采用即时切换。

## 7. 视觉与可访问性基线

- 主色采用低饱和青绿，辅以暖白背景和深色正文；完成、警告、错误使用独立语义色。
- 不用紫色渐变、装饰性光球或纯视觉噪声作为主视觉。
- 功能图标使用统一图标库，图标按钮必须有可访问名称和悬停说明。
- 正文基准字号不小于16px，普通文本对比度至少4.5:1。
- 可点击控件使用语义化按钮或链接，触控目标至少44×44px。
- 键盘操作有可见焦点，弹出面板有焦点管理和合理返回路径。
- 状态不能只用颜色表达，同时使用文字、图标或结构差异。
- 动画只用于表达空间连续性和状态变化，并遵守 `prefers-reduced-motion`。

## 8. 全局未知情况处理

Agent遇到未预设组合情况时，遵循统一策略，而不是寻找固定话术：

```text
识别当前阶段和状态
→ 判断用户意图与影响范围
→ 查询允许动作和已有证据
→ 尝试最小且可恢复的处理
→ 需要关键缺失信息时只询问一个澄清问题
→ 说明结果、限制和下一步
→ 写入系统事件
```

测试不要求逐字匹配回答，而检查：状态是否正确、事实是否来自当前数据、是否越权、是否给出恢复方案、是否同步更新工作台和对话事件。

## 9. 三阶段统一组件清单

- `AppShell`：顶部栏、阶段轨道、折叠导航和响应式容器。
- `ConversationTimeline`：用户消息、Agent气泡、系统操作卡片和证据卡。
- `Composer`：文本输入、上传、链接和当前阶段入口。
- `StageWorkbench`：统一右栏容器，内部按阶段替换内容。
- `EvidenceDrawer`：统一证据引用与来源定位。
- `OperationCard`：操作结果、影响摘要、撤销和恢复。
- `StatusBadge`：处理中、待确认、已完成、需处理、失败可重试等语义状态。
- `StageRail`：阶段位置、完成度和前置条件。
- `ConfirmDialog`：高影响操作确认与结构化变更预览。

组件的视觉样式和交互契约保持稳定，阶段文稿只定义各自工作台需要传入的数据和允许动作。

## 10. 验收标准

- 阶段一、二、三使用相同页面外壳，切换阶段后用户仍能识别输入区、阶段轨道、工作台和证据入口。
- 任意工作台操作都会在对话区出现系统操作卡片，并可在事件记录中回溯。
- Agent业务回答没有预置整段答案，能引用当前项目、状态和证据。
- 右侧工作台在桌面端常驻，在窄屏端从右侧滑出，且不产生核心内容横向溢出。
- 已完成阶段可以回看，未满足前置条件的阶段不可越权进入。
- 证据卡在三个阶段都使用统一编号、定位和展开交互。
- 键盘、焦点、对比度、触控尺寸和减少动效符合基线。
- 未预设的多轮组合场景能够安全澄清、降级、恢复并留下完整事件。

## 11. 与阶段设计文稿的关系

本文件是前三个阶段的全局交互约束。阶段一、二、三各自的设计文稿必须引用本文件，并只补充：

- 本阶段工作台的具体信息结构。
- 本阶段允许的对话动作和状态动作。
- 本阶段专属的证据字段和反馈内容。
- 本阶段的复杂多轮场景与验收用例。

阶段文稿不得重新定义页面主布局、对话内容类型、操作卡片、证据抽屉和响应式行为，除非后续全局设计经过重新讨论并形成新版本。
